Позволяет приложениям получать информацию о самих себе и своем окружении без необходимости прямого обращения к kubernetes API, то есть в обход RBAC и прочего. Данные можно передать только через env и файлы в `volume`. 

### Использование через env

Это делается с помощью поля `valueFrom.fieldRef` в определении переменной

В `fieldPath` можно указать различные поля из спецификации пода, наиболее часто встречающиеся:
- `metadata.name`
- `metadata.namespace`
- `status.podIP`
- `spec.nodeName`
- `spec.serviceAccontName`
- `metadata.labels['<key>']`
- `metadata.annotations['<key>']`

```
kubectl -n work logs downward-api-env-demo
```

### Использование через volume

Другой способ - смотрировать информацию как файлы в `volume` типа `downwardAPI`. Этот метод более гибкий, так как позволяет передавать не только поля (`fieldRef`), но и информацию о ресурсах контейнера (`resourceFieldRef`), например, лимиты CPU или памяти.

### Динамическое обновление данных

Ключевое преимущество `downwardAPI` при использовании `volume` заключается в том, что данные в файлах обновляются автоматически при изменении метаданных пода. В отличие от переменных окружения, которые устанавливаются один раз при запуске контейнера, файлы в `downwardAPI volume` отражают актуальное состояние ресурса

Создадим под, который будет периодически считывать свои метки и выводить их в лог, затем изменим одну из меток и убедимся, что приложение внутри контейнера увидит это изменение

```
kubectl -n work logs -f downward-api-pod
```

Не прерывая выполнение предыдущей команды, изменим `status`

```
kubectl -n work label pod downward-api-pod status=running --overwrite
```

Этот механизм позволяет создавать приложения, которые могут динамически реагировать на изменения в своей конфигурации или состоянии в k8s без необходимости прямого обращения к API.

Динамической изменение работает как в `ConfigMap`, то есть создается новая директория и меняется символьная ссылка уже на нее
