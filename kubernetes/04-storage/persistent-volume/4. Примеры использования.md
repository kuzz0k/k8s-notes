
### Deployment

Создадим `StorageClass`, сам `Deployment` вместе с `PVC`

```
kubectl -f apply storage-class.yaml
kubectl -n work apply -f deployment.yaml
```

Сразу проверим, что внутри

```
kubectl -n work get pod,deployment,pv,pvc -l app.kubernetes.io/name=multi-replica-deployment
```

Теперь удалим `PVC` и `Deployment` через манифест, чтобы посмотреть как сработает `Reclaim Policy`

```
kubectl -n work delete -f deployment.yaml --force --grace-period=0
```

### Deployment с двумя репликами

Создадим `Deployment`, в котором две реплики будут писать под и дату, посмотрим файл с логами

```
kubectl -n work exec $(kubectl -n work get pods -l app.kubernetes.io/name=multi-replica-deployment -o jsonpath='{.items[0].metadata.name}') -- cat /data/out.txt
```

Увидим, что поочередно поды записывают лог, удалим ради эксперимента один из подов:

kubectl -n work delete pod multi-replica-deployment-665868ff68-ktlqx --force --grace-period=0

Заметим, что после создания нового пода после удаления, он имеет уже новое название. Из этого следует несколько проблем `Deployment`:
- **Общее хранилище для всех реплик** — все поды используют один и тот же `PVC`. Если приложение не рассчитано на параллельную работу с общим каталогом (нет блокировок, координации, разбиения данных по подам), это приводит к **повреждению данных** и гонкам записи.
- **Нестабильная идентичность** — при пересоздании пода он получает случайное имя. Приложение не может рассчитывать на предсказуемое имя, стабильный сетевой идентификатор и порядок запуска. Следствия: нельзя привязать конкретный `PVC` к конкретному поду, нельзя назначить стабильный DNS-адрес, нельзя гарантировать порядок старта/остановки, данные в общем `PVC` смешиваются между репликами.
- **Ограничение ReadWriteOnce** — если `StorageClass` поддерживает только `ReadWriteOnce`(например, большинство блочных CSI: `local-path` в k3s, `ebs.csi.aws.com`, `csi-hostpath`), то в этом случае только один под запустится, остальные будут ждать. Том можно смонтировать только на одну ноду, поэтому при масштабировании новые реплики останутся в `Pending` или `ContainerCreating`.
- **Конкурентный доступ к файлам** — даже с `ReadWriteMany` одновременная запись в один файл приводит к потере данных, повреждению файла и непредсказуемому результату. POSIX-блокировки поверх NFS работают не всегда и зависят от версии NFS и опций монтирования. Приложения с параллельной записью в общий файл обычно требуют явной синхронизации на уровне кода.


Поэтому, когда мы говорим о четком распределении данных, о их четком сохранении, то `Deployment`, `PVC` для этого использовать не надо

### StatefulSet и volumeClaimTemplates

Одной из ключевых особенностей `StatefulSet` является возможность автоматически создавать `PersistentVolumeClaim` для каждой реплики с помощью шаблона — `volumeClaimTemplates`.

### volumeClaimTemplates

Когда вы определяете `volumeClaimTemplates` в манифесте `StatefulSet`:

1. Для каждой реплики `StatefulSet` (например, `app-0`, `app-1`) автоматически создается **свой**`PVC`.
2. Имя `PVC` формируется по шаблону: `<имя-шаблона>-<имя-пода>`. Например, если имя шаблона `www`, а имя пода `app-0`, то `PVC` будет называться `www-app-0`.
3. В каждом `PVC` определяется `StorageClass`, что приводит к динамическому созданию уникального `PV` для каждой реплики.
4. Созданный `PVC` автоматически монтируется к соответствующему поду.

В отличие от `Deployment` в `StatefulSet` есть `volumeClaimTemplates'

```
volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "nfs-client"
      resources:
        requests:
          storage: 1Gi
```

Также не забудем `headless` сервис для `StatefulSet`

```
---
apiVersion: v1
kind: Service
metadata:
  name: nginx
  labels: &labels
    app.kubernetes.io/name: web
    app.kubernetes.io/instance: test
    app.kubernetes.io/version: v0.0.1
spec:
  ports:
    - port: 80
      name: web
  clusterIP: None
  selector: *labels
```

Применим манифест и посмотрим, какие ресурсы мы получаем

```
kubectl -n work get statefulset,pod,pvc
```

Теперь уже на каждый под выделяется отдельный `PVC`, причем после удаления манифеста `PVC` остаются и после перезапуска поды подключатся к тем же `PVC`

```
kubectl -n work delete pvc www-stateful-app-0 www-stateful-app-1
```
