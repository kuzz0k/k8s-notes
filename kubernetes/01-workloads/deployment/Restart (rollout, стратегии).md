Рестартнуть можно руками через 
```
kubectl -n work rollout restart deployment my-pod
```

При изменении шаблона Pod (например, версии образа):

```
image: nginx:1.30
↓
image: nginx:1.31
```

Kubernetes не изменяет существующий ReplicaSet.

Вместо этого:

1. Создаётся **новый ReplicaSet**.
2. Запускается механизм **Rolling Update**.
3. Новый ReplicaSet постепенно создаёт новые Pod.
4. Старый ReplicaSet постепенно уменьшает количество своих Pod.
5. После успешного обновления старый ReplicaSet масштабируется до `0` реплик и сохраняется для возможного отката.

```
Deployment
      │
      ▼
RS v1 (3 Pods)
      │
      ▼
Изменение Deployment
      │
      ▼
Создаётся RS v2
      │
      ▼
Rolling Update
+1 новый Pod
-1 старый Pod
+1 новый Pod
-1 старый Pod
...
      │
      ▼
RS v1 = 0 Pods
RS v2 = 3 Pods
```

---

# revisionHistoryLimit

Определяет, сколько старых ReplicaSet хранить после обновлений.

```
revisionHistoryLimit: 10
```

По умолчанию хранится **10** предыдущих ReplicaSet.

Это позволяет выполнять:

```
kubectl rollout undo deployment <deployment-name>
```

Если установить:

```
revisionHistoryLimit: 0
```

старые ReplicaSet сохраняться не будут, и откат станет невозможен.

# Strategy

Определяет способ обновления Pod.

## RollingUpdate (по умолчанию)

```
strategy:
  type: RollingUpdate
```

Обновление происходит постепенно:

- создаются новые Pod;
- после их готовности удаляются старые;
- приложение продолжает работать без простоя.

Дополнительные параметры:

- `maxSurge` — сколько дополнительных Pod можно создать сверх желаемого количества.
- `maxUnavailable` — сколько Pod одновременно может быть недоступно.

---

## Recreate

```
strategy:
  type: Recreate
```

Все старые Pod сначала удаляются, затем создаются новые.

```
Old Pods
↓↓↓
Удаление всех
↓↓↓
Создание новых
```

Используется редко, так как во время обновления возникает простой приложения (Downtime). Подходит для приложений, которые не поддерживают одновременную работу разных версий.
